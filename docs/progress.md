### Indic romanized query-path — Hindi ✅ DONE
Users can type Hindi in the Latin alphabet (`bharat ki rajdhani kya hai`) and hit the
native-Devanagari index. See `docs/indic-romanized-spike.md` for the motivating spike.
- ✅ `Transliterator` **port** + adapters (`transliteration/`): **google** (default — googletrans,
  best quality, free, network per query, local rule-based fallback baked in), **indicxlit** (local
  offline neural, `psidharth567/indic-xlit-50M`, pinned; feasibility-proven on Py3.13),
  **rule-based** (`indic-transliteration`), **llm** (reuses the generation endpoint). Env-driven
  via `TRANSLITERATION_PROVIDER`.
- ✅ **Design pivoted on eval evidence.** First built dual-query (search raw + transliterated,
  fuse). The eval showed *every* fusion (max-cosine, RRF, confidence-routing) dragged Hindi recall
  *below* pure transliteration (~0.56 vs ~0.67) — the raw search's noise is unavoidable when you
  can't tell which form is right. Switched to **detection** (`transliteration/detect.py`): a cheap
  distinctly-Hindi function-word check (`kya`/`hai`/`kaun`/`nahi`, English collisions excluded)
  decides *whether* to transliterate. Detected → search the transliterated form; plain English →
  raw, untouched.
- ✅ Measured (XQuAD-hi, 10k distractors, 150 queries, google, recall@5): native **0.947** ·
  romanized-raw **0.204** · transliterated **0.676** · **shipped 0.669**. ⚠️ **Superseded** —
  measured on the pre-fix harness (queries generated by the library under test); the same
  configuration now scores **0.917** shipped retention. See Phase 8b under M19.
  Romanized recovers
  **0.20 → 0.67 (3.3×)**; detection recall **98.7%**, so shipped ≈ the transliterated ceiling;
  **0 English false positives**. (Below the spike's 0.747 LLM figure — that was a different corpus
  cut; the ceiling here is google's transliteration on English-name-heavy XQuAD-hi.)
- ✅ Eval tooling: `hi` added to `build_eval_corpus.py`; `scripts/eval_romanized.py` (romanizer +
  4 conditions). Live-verified through the real `RetrievalService` (bge-m3 + Chroma + google):
  romanized→correct doc, English not transliterated (and still cross-lingual). 109 passed, gates green.
- ✅ **Opt-in MuRIL detector** (`TRANSLITERATION_DETECTOR=muril`): a frozen `google/muril-base-cased`
  feature extractor (`transliteration/muril.py`, pinned) + a LogisticRegression head
  (`scripts/train_romanized_detector.py`, artifact `data/models/romanized_indic_detector.joblib`,
  KB-sized, committed). Started as a binary Hindi head; **now multinomial (hi/kn/te/other)** — see the
  local-multi-class section below. Default stays **word-list** (fast, no model, hermetic tests); MuRIL
  loads lazily on CPU only when opted in, with word-list fallback on any failure.
- **Deferred:** full MuRIL fine-tune; MuRIL for retrieval (the actual ~0.67 ceiling).

## M19 — Agentic RAG on LangGraph ✅

Replaced the hand-rolled orchestration with a LangGraph state machine that grades its own retrieval
and repairs it, and streams its reasoning to the chat UI. **The graph is now the only
orchestration** — all three routes go through it.

**The result is parity, not a win, and that is the finding.** The eval (phase 8) caught the agent
*regressing* twice before the default landed somewhere defensible. Full story below; the short
version is that on this corpus no cosine threshold can tell a weak-but-correct retrieval from a
wrong one, so the free grader is restricted to the one signal it can trust.

**The real motivation, found during exploration:** condense → retrieve → generate is implemented
*three times* — `RagQueryService.answer_query` (sync), `RagQueryService.answer` (sync), and
`StreamingAnswerGenerator.stream` (async) — with a `cast(RagQueryService, …).retrieval_service`
reach-through in `chat_stream.py` holding two of them together so the 2.2 GB model isn't loaded
twice. This is a de-duplication that happens to buy agentic behaviour, not agent theatre.

### Phase 8 — eval ✅ (and it changed the design twice)

Added a fifth `agentic` condition to `scripts/eval_romanized.py` that drives the **real graph** —
same nodes, routers and repair logic the API uses — with only generation stubbed, so the eval stays
free and offline like every other condition. A `CountingRetriever` makes repairs observable, and
`--relevance-threshold` / `--max-repairs` expose the knobs.

**It immediately proved the agent was making retrieval worse**, and then — after the harness itself
was fixed (see below) — that it is exactly neutral. Final measurement: XQuAD-hi, 3240 docs, 60
queries, google transliterator, human-written romanized queries, k=5:

| condition | recall@5 | MRR | retention |
|---|---|---|---|
| native | 1.000 | 0.981 | 1.000 |
| romanized-raw | 0.500 | 0.378 | 0.500 |
| transliterated | 0.917 | 0.856 | 0.917 |
| shipped | 0.917 | 0.856 | 0.917 |
| **agentic** | **0.917** | 0.856 | 0.917 |

`agent repaired: 0/60`. ⚠️ **Sampled** — 60 queries / 3240 docs, not the documented 150 / 20,240.
Not a drop-in replacement for the old 0.669; more distractors will pull it down.

The path there, and why the final answer is parity rather than a win:

1. **First run, threshold 0.35: repair never fired.** The entire score range is 0.389–0.696, so the
   default I had guessed was inert — exactly the risk flagged in phase 2.
2. **Probed the distribution instead of guessing again.** Top-1 cosine for *correct* retrievals:
   min 0.424 / median 0.524. For *incorrect*: max 0.462 / median 0.431. **The bands overlap.** The
   best separating floor (0.45) fires on 14/60 queries and only 8 are real misses.
3. **At 0.45 the agent lost: 0.733 vs 0.800.** Repair replaced 6 correct-but-low-scoring
   retrievals with the raw romanized query, whose recall is 0.133.
4. **Fix 1 — never regress.** Generation now answers from the *best* attempt (`best_context`), not
   the last. 0.733 → 0.750. Still losing.
5. **Fix 2 — stop comparing attempts by score.** Choosing between a transliterated and a raw search
   by cosine is precisely the *relative* judgement `transliteration/detect.py` already recorded as
   unreliable ("the raw romanized search finds enough high-cosine noise to look confident"). A
   repair is now adopted only if it flips weak→relevant. 0.750 → 0.767. **Still losing.**
6. **Conclusion — set the default floor to 0.0.** The free grader keeps only the arm it can defend:
   an *empty* retrieval, which is 100% reliable. Repair then fires 0/60 here and the agent is at
   exact parity with the plain pipeline, 0.800.

So the honest headline: **the repair machinery is correct and provably safe, and on this corpus it
is neutral.** Three selection rules all lost to the plain pipeline before the floor came down. That
is the same conclusion the earlier fusion experiment reached, reproduced in the agentic setting —
the raw romanized search is irreducible noise, and no amount of cleverness at selection time
recovers it.

### Phase 8b — the eval was rigged, and fixing it changed the picture ✅

While chasing why the repair loop never helped, a diagnostic turned up something worse than a
disappointing feature: **the harness was scoring a transliteration adapter against its own
inverse.**

`eval_romanized.py` synthesized its romanized test queries with `indic_transliteration.sanscript`
(Devanagari → IAST → strip diacritics). The `rule-based` adapter *under test* is that same library.
So one of the things being measured was being handed input generated by its own character mapping.
Measured effect: rule-based 0.950 vs google 0.700 on identical queries. It also produced text no
human would ever type — `josa narmana ne kitane bala ko imtarasepta kiya` for what a person writes
as `josh norman ne kitane ball co intercept kiya`.

**Fix** (`scripts/build_romanization_lexicon.py` → `data/eval/romanization_hi.json`, 66 KB):
queries are now built from **human-written** romanizations, word by word — Dakshina's crowd-collected
per-word attestations plus a word-aligned Hindi↔roman parallel corpus, neither of which involves
`indic_transliteration`. 86% of query words are covered; the rest still fall back to sanscript and
**every run prints that share** rather than hiding it. The logic lives in
`evaluation/romanization.py`, not `scripts/`, so it is covered by tests and `mypy --strict` — 18
tests, including one asserting that covered words do *not* reproduce the rule-based scheme.

**What the fix revealed:**

| | rigged queries | human queries |
|---|---|---|
| google (shipped) | 0.700 | **0.800** |
| rule-based | **0.950** | 0.850 |
| rule-based's edge | **+0.250** | +0.050 |
| fallback rescued a miss | 5/20 | 4/20 |
| fallback **broke** a hit | **0/20** | **3/20** |

Two consequences, both important:

1. **The shipped romanized path is much better than published.** 0.917 retention (sampled) against
   the recorded 0.669 — the old number was depressed by measuring against queries nobody types.
   `romanized-raw` tells the same story from the other side: 0.500 rather than 0.133, because real
   romanized Hindi contains English proper nouns that bge-m3 matches cross-lingually.
2. **It killed a feature of mine.** `retransliterate` (retry through a second renderer) was built
   on that "rescues 5, breaks 0" row — which was an artifact. On honest queries it rescues 4 and
   breaks 3: net +1 on n=20, i.e. noise. **Removed**, along with `transliteration_fallback_provider`
   and the `use_fallback` plumbing.
